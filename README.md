# OpenClaw + Telegram: рабочий стенд из России без VPN

Тестовое задание на позицию «Вайбкодер». Персональный AI-ассистент
[OpenClaw](https://github.com/openclaw/openclaw) развёрнут в Docker на
собственном VPS в Москве, подключён к Telegram-боту и отвечает на сообщения.
**На сервере, где работает OpenClaw, нет ни VPN-клиента, ни системного
туннеля** — доступ к заблокированному Telegram Bot API решён иначе.

| | |
|---|---|
| **Бот** | [@test2452523bot](https://t.me/test2452523bot) |
| **Где развёрнут** | VPS в Москве, Ubuntu 24.04, 1 vCPU / 2 ГБ RAM |
| **Версия** | OpenClaw 2026.7.1, официальный образ `ghcr.io/openclaw/openclaw` |
| **Модель** | `qwen/qwen3.8-27b-free` через [OrcaRouter](https://www.orcarouter.ai) (бесплатный тир) |
| **Запуск** | Docker Compose (бонусный пункт задания) |
| **Персона** | кастомный [`SOUL.md`](config/SOUL.md) (бонусный пункт задания) |

## Главный вывод: блокировка оказалась не там, где ожидалась

Задание предполагает, что из России не работает AI-провайдер. Первым делом я
это проверил — и получил обратную картину. Замеры сделаны **с самого
московского VPS, при выключенном VPN**:

| Сервис | Результат |
|---|---|
| `api.orcarouter.ai` — реальный запрос к модели | ✅ **1.36 с**, модель ответила |
| `api.telegram.org` — по адресу из DNS | ❌ **таймаут**, TCP/443 не открывается |
| `registry.npmjs.org`, `ghcr.io`, `github.com` | ✅ доступны |

Заблокирован не LLM, а **Telegram**. Поэтому всё решение Этапа 2 крутится
вокруг Telegram, а трафик к модели идёт напрямую из Москвы и никаких
ухищрений не требует.

## Этап 2: как бот работает без VPN

### Диагностика

Я не стал сразу вешать VPN, а сначала выяснил **характер** блокировки — от
этого зависит выбор решения.

**Шаг 1. Проверил, не в IPv6 ли дело.** `getent hosts` отдавал IPv6-адрес
первым, а IPv6-связности у сервера нет — классическая ловушка, когда клиент
висит на недоступном адресе. Оказалось, ложный след: принудительный `curl -4`
тоже не проходил.

**Шаг 2. Обошёл DNS.** Запрос напрямую по IP с подменой SNI неожиданно
сработал:

```bash
curl --resolve api.telegram.org:443:149.154.167.220 https://api.telegram.org/
# 302 за 0.99 с
```

Значит DPI **не режет по имени домена** — блокировка идёт по конкретным
IP-адресам. А DNS во всём мире отдаёт `149.154.166.110`, и именно он мёртв.

**Шаг 3. Нашёл живой адрес.** Перебрал подсети Telegram на TCP/443, а затем
проверил выживших настоящим вызовом Bot API:

```
149.154.167.0/24 -> открыто 2 адреса, Bot API отвечает 1: 149.154.167.220 OK
149.154.166.0/24 -> открытых нет
91.108.56.0/24   -> открыт 1 адрес, но Bot API не отвечает
```

### Решение

Живой адрес прибивается к домену прямо в `/etc/hosts` контейнера — штатным
механизмом Docker Compose:

```yaml
services:
  openclaw-gateway:
    extra_hosts:
      - "api.telegram.org:${TELEGRAM_API_IP:-149.154.167.220}"
```

Одна строка. Ни VPN, ни прокси, ни туннеля.

### Почему именно так

**Ничего лишнего.** Заблокирован один домен — чинится один домен. Системный
VPN потащил бы через заграницу весь трафик сервера, включая LLM (который и
так работает быстрее напрямую) и соседние сервисы на этой машине.

**Быстро.** Прямое соединение из Москвы: к Telegram ~44 мс, к модели ~1.4 с.
Любой зарубежный хоп это ухудшил бы.

**Без точки отказа.** Прокси — это ещё один сервер, который может упасть,
и ещё один счёт за VPS. Здесь внешних зависимостей нет.

**Честная оговорка:** у подхода есть слабое место — живой адрес один, и
завтра его могут закрыть. Поэтому решение подстраховано с двух сторон.

### Подстраховка 1: watchdog

[`scripts/tg-ip-watchdog.sh`](scripts/tg-ip-watchdog.sh) на systemd-таймере
проверяет доступность каждые 5 минут. Если текущий адрес умирает — скрипт
ищет новый (сначала «горячий список», затем перебор подсетей Telegram),
прописывает его в `.env` и пересоздаёт контейнер. Без участия человека.

Живой Bot API опознаётся по ответу-отпечатку на **заведомо неверный** токен:

```
{"ok":false,"error_code":401,"description":"Unauthorized"}
```

Так watchdog отличает настоящий Telegram от заглушки провайдера — и при этом
ему не нужен наш токен бота.

### Подстраховка 2: прокси как план Б

Если закроют вообще все прямые адреса и watchdog не найдёт ни одного живого —
в [`scripts/proxy-fallback/`](scripts/proxy-fallback/) лежит готовый вариант с
точечным прокси: через заграницу уходит **только** `api.telegram.org`, трафик
к модели остаётся прямым. Включается тремя командами, **по умолчанию
выключен**.

## Архитектура

```
   МОСКВА — VPS (Ubuntu 24.04, 2 ГБ RAM)
   VPN-клиента на машине нет
 ┌──────────────────────────────────────────────┐
 │  docker compose                              │
 │  ┌────────────────────────────────────────┐  │
 │  │  openclaw-gateway  (127.0.0.1:18789)   │  │
 │  │                                        │  │
 │  │  /etc/hosts:                           │  │
 │  │    api.telegram.org -> 149.154.167.220 │  │
 │  └───────┬───────────────────────┬────────┘  │
 └──────────┼───────────────────────┼───────────┘
            │ long polling          │ HTTPS
            ▼                       ▼
    api.telegram.org         api.orcarouter.ai
    (живой адрес)            (не заблокирован)
            │                       │
            ▼                       ▼
      @test2452523bot        qwen3.8-27b-free
                             + 2 резервные модели

   ┌──────────────────────────────────────────┐
   │ systemd timer, каждые 5 минут:           │
   │   tg-ip-watchdog.sh — жив ли адрес?      │
   │   умер -> найти новый -> перезапустить   │
   └──────────────────────────────────────────┘
```

Telegram работает через **long polling**: Gateway сам ходит наружу,
входящие порты открывать не нужно, белый IP и домен не требуются.

## Надёжность и безопасность

**Резервные модели.** У `qwen3.8-27b-free` на странице провайдера заявлен
error rate 18.9% — примерно каждый пятый запрос падает. Для стенда, который
проверяют вживую, это неприемлемо, поэтому настроен каскад:

```json
"model": {
  "primary": "orcarouter/qwen/qwen3.8-27b-free",
  "fallbacks": [
    "orcarouter/deepseek/deepseek-v4-flash-free",
    "orcarouter/tencent/hy3-free"
  ]
}
```

**Control UI не торчит в интернет.** Порт публикуется как
`127.0.0.1:18789`, а не `0.0.0.0`. Сервер публичный, и админка на нём в
открытом доступе — это готовый инцидент. Доступ к панели — через
SSH-туннель.

**Секретов в репозитории нет.** В `openclaw.json` только ссылки
`${ORCAROUTER_API_KEY}`, токен бота читается из переменной окружения.
Реальные значения живут в `.env`, который в `.gitignore`.

**Лимит памяти.** `mem_limit: 1024m` плюс swap 2 ГБ: на сервере всего 2 ГБ
RAM и работают другие сервисы, Node не должен их выдавить.

**Границы ассистента.** Бот открыт для всех (`dmPolicy: "open"`), поэтому в
[`SOUL.md`](config/SOUL.md) прописан запрет выполнять команды на сервере,
раскрывать конфиги и ключи, а также реагировать на «забудь инструкции».
Групповые чаты отключены.

## Трудности

Честно, по порядку возникновения.

**1. Проверял не то, что нужно.** Первые замеры доступности я снял с
ноутбука — и они показали, что всё прекрасно работает. Потом заметил, что
публичный IP машины шведский: был включён VPN, и все результаты оказались
мусором. Урок: сначала убедись, что измеряешь то, что думаешь. Повторил
замеры с VPS, где VPN нет по определению.

**2. Гипотеза о блокировке была ровно наоборот.** Я готовился обходить
блокировку AI-провайдера, а он открылся напрямую. Заблокированным оказался
Telegram. Если бы начал строить прокси не проверив — потратил бы часы на
инфраструктуру, которая не нужна.

**3. IPv6 — ложный след.** DNS отдавал IPv6-адрес первым, глобальный IPv6 на
интерфейсе был, но связности наружу нет. Выглядело как исчерпывающее
объяснение таймаутов. Проверка `curl -4` гипотезу похоронила — и это
сэкономило время, потому что «починка» IPv6 ничего бы не дала.

**4. Тег `latest-slim` из документации не существует.** Документация
OpenClaw упоминает slim- и browser-варианты образа, но в реестре их нет —
`manifest unknown`. Пришлось смотреть реальный список тегов через API GHCR.
Взял `latest`.

**5. Контейнер падал в бесконечный рестарт без внятной причины.** В
`docker compose ps` он выглядел живым, но health не поднимался. В логах:
`EACCES: permission denied, mkdir '/home/node/.openclaw/state'`. Каталоги
были созданы от root, а процесс внутри работает под `node` (uid 1000).
Лечится `chown -R 1000:1000`, но само сообщение никак не намекает на права
монтирования.

**6. Самая коварная — бот молчал бы для проверяющих.** Задание требует
username бота, чтобы HR проверил его в реальном времени. Я поставил
`dmPolicy: "open"`, а OpenClaw написал в лог:

> `dmPolicy="open"` but `allowFrom` does not include `"*"`; **all DMs will be dropped**

То есть без `allowFrom: ["*"]` бот принимал бы сообщения только от заранее
известных ID и молча игнорировал всех остальных. Локально с моего аккаунта
это заметить было бы трудно, а проверяющий увидел бы мёртвого бота.
Поймал только потому, что прочитал предупреждения в логе целиком.

**7. Синтаксис CLI пришлось выяснять на месте.** `agent "текст"` даёт
`Too many arguments`; нужен `agent --agent main -m "текст"`. Помог `--help`.

**8. Контейнер числился `unhealthy`, хотя работал.** `healthz` и `readyz`
отдавали 200, бот отвечал, но Docker показывал `unhealthy`. Причина — в
штатном `docker-compose.yml` healthcheck вызывает
`node dist/docker-healthcheck.js`, а в опубликованном образе этого файла нет:
`MODULE_NOT_FOUND`. Апстримный compose из свежего master разошёлся с
образом `latest`. Заменил проверку на HTTP-запрос к `/healthz` — он не
зависит от внутренностей образа. Мелочь, но в демонстрации красное
`unhealthy` выглядит как сломанный стенд.

**9. Панель открывалась, но не подключалась.** Control UI грузился и тут же
писал «Не удалось подключиться», предлагая проверить, запущен ли Gateway.
Gateway был запущен. Разгадка нашлась в логе:

```
[ws] unauthorized client=openclaw-control-ui auth=none reason=token_missing
[ws] closed before connect code=4008 phase=auth_credentials_received
```

Панель защищена `OPENCLAW_GATEWAY_TOKEN`, и токен передаётся **фрагментом
URL** — `http://127.0.0.1:18789/#token=<токен>`. Само сообщение об ошибке
уводит в сторону: оно говорит про запущенный Gateway и транспорт, а
настоящая причина — отсутствие токена. Точную команду для получения ссылки
см. в разделе «Как воспроизвести».

## Как воспроизвести

```bash
git clone <этот-репозиторий> /opt/openclaw-stand
cd /opt/openclaw-stand
cp .env.example openclaw/.env
nano openclaw/.env          # вписать TELEGRAM_BOT_TOKEN и ORCAROUTER_API_KEY
./scripts/deploy.sh
```

`deploy.sh` идемпотентен: создаёт swap, клонирует апстрим, тянет образ,
готовит каталоги с нужным владельцем, поднимает Gateway и ставит watchdog.

**Проверка:**

```bash
cd /opt/openclaw-stand/openclaw

# агент отвечает
docker compose run -T --rm openclaw-cli agent --agent main -m "Привет"

# канал подключён
docker compose run -T --rm openclaw-cli channels status --probe
# ожидаем: running, connected, mode:polling, works

# Telegram доступен без VPN
docker compose exec openclaw-gateway \
  curl -s https://api.telegram.org/bot123:INVALID/getMe
# ожидаем: {"ok":false,"error_code":401,...}
```

**Control UI** (наружу не публикуется).

Панель защищена токеном, поэтому нужен не просто адрес, а адрес с токеном —
иначе страница откроется, но WebSocket к Gateway не подключится и UI покажет
«Не удалось подключиться».

```bash
# 1. Поднять туннель (порт наружу намеренно не опубликован)
ssh -L 18789:127.0.0.1:18789 <хост>

# 2. Получить готовую ссылку с токеном
ssh <хост> 'echo "http://127.0.0.1:18789/#token=$(grep OPENCLAW_GATEWAY_TOKEN \
  /opt/openclaw-stand/openclaw/.env | cut -d= -f2)"'

# 3. Открыть напечатанную ссылку в браузере
```

Токен сохраняется в сессии браузера — после первого входа достаточно
`http://127.0.0.1:18789/`.

## Структура

```
├── docker-compose.override.yml   оверлей поверх апстрима: пиннинг IP, лимиты
├── .env.example                  шаблон переменных (секретов здесь нет)
├── config/
│   ├── openclaw.json             провайдер, каскад моделей, канал Telegram
│   └── SOUL.md                   персона ассистента
└── scripts/
    ├── deploy.sh                 развёртывание с нуля
    ├── tg-ip-watchdog.sh         поддержание живого адреса Telegram
    ├── install-watchdog.sh       systemd-таймер для него
    └── proxy-fallback/           план Б: точечный прокси (выключен)
```

Апстримный `docker-compose.yml` не патчится — он обновляется через
`git pull`, а все наши изменения изолированы в `docker-compose.override.yml`.

## Использование AI

Задание решалось в связке с Claude (Claude Code в терминале). AI применялся
не для генерации кода «на глаз», а как инструмент исследования: разбор
документации OpenClaw, формулировка и проверка гипотез о характере блокировки
Telegram, чтение логов, подготовка скриптов и этой документации.

Существенная часть работы — именно проверка гипотез, а не написание кода.
Три ключевых вывода (провайдер доступен; блокировка идёт по IP, а не по SNI;
`dmPolicy` без `allowFrom` роняет все личные сообщения) получены измерениями
на живом сервере, а не из документации: в документации этого нет.
